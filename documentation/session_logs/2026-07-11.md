## 2026-07-11 — Runtime config option for DPAD left/right card navigation in detail view

**Worked on:**
- Added `enable_card_detail_navigation` runtime config option (default TRUE) to toggle DPAD left/right card switching in the card detail view.
- In deck context: LEFT/RIGHT navigates through the current deck's cards (linear, stops at bounds).
- In trunk context: LEFT/RIGHT navigates through the trunk's full card list (wraps around like trunk scrolling).
- Deck nav context set explicitly in `DeckMenuShowSelectedCardDetails`.
- Trunk nav context auto-detected from `gTrunkMenu.cursorState == TRUNK_CURSOR_DETAILS`.
- Used `goto render_card` pattern to rebuild description + re-render card art via `sub_800B618` when switching cards.
- Navigation globals allocated via `_kernel_malloc_ewram` in `ram_map_ewram.s` (not COMMON — the linker discards COMMON).
- Extracted `CardDetailViewBuildDescription` and `CardDetailViewRenderPage` helpers to avoid duplication with the goto.

**Files touched:**
- `configs/runtime.h` — added `enable_card_detail_navigation` field
- `configs/runtime.c` — set default TRUE
- `asm/ram_map_ewram.s` — allocated `gCardDetailNavActive`, `gCardDetailNavIndex`
- `src_custom/code_801EF30_hooks.c` — DPAD LEFT/RIGHT handlers + rebuilt helpers
- `src_custom/deck_menu_hooks.c` — set nav context in `DeckMenuShowSelectedCardDetails`
- `src_custom/trunk_hooks.c` — made `GetTrunkCardCount` non-static

**Outcome:** `make test-cards-build` passes. Feature is disabled when `enable_card_detail_navigation = FALSE`, inactive in shop/password/duel contexts.

**Open / next:**
- Duel field details (right-click on a field monster) could also benefit from LEFT/RIGHT nav, but that's a separate enhancement.

**Root cause:** The `_kernel_malloc_ewram` macro in `asm/ram_map_ewram.s` just decremented `UsedFreeEwramSpaceTop` by `\size` with no alignment. A preceding 1-byte allocation (`gDebugAiBothSidesMode` at `0x0203DBB4`) pushed the cursor to `0x0203DBB5`, and `gRuntimeConfigEwram` (0x60 bytes) landed at that odd address `0x0203DBB5`.

The `CpuSet` BIOS call with 32-bit mode (`CPU_SET_32BIT | 21`) writes to word-aligned destinations. On mGBA (accurate), the destination was masked to `0x0203DBB4`, causing every struct byte to read the wrong data (off-by-one). no$gba is lenient about the alignment and used the address as-is.

**Also reverted:** a mistaken `CPU_SET_32BIT`/`CPU_SET_SRC_FIXED` swap in `include/gba/syscall.h`. The original constants were correct — bit 24 = source fixed, bit 26 = 32-bit transfer per GBATEK docs. `CpuCopy32` calls in the vanilla overworld code (e.g. `CpuCopy32(gBgVram.sbb1B, (void*)0x600D800, 0xE20)`) proved the original values work.

**Fix:** Added `& ~3` word-alignment after the size subtraction in both `_kernel_malloc_ewram` and `_kernel_malloc_ewram_array` macros.

**Files touched:**
- `asm/ram_map_ewram.s` — Added alignment to both allocator macros
- `include/gba/syscall.h` — Reverted to original (correct) constant values

**Outcome:** `make test-cards-build` passes (19/19 tests, clean link). `gRuntimeConfigEwram` now at `0x0203DB70` (word-aligned).
